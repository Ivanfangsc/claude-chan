# 用视频模型做“看不出循环”的桌宠动画

Claude-Chan 的全部动画都是在本机用开源视频模型生成的：一张立绘出发，做出 9 个状态的关键帧，再生成持续动作的 loop、状态之间的过渡、插进 loop 里的随机小动作、只多一次眨眼的 loop 变体，最后抠图导出成桌宠播放的透明动画。

这份文档记录我们最后用下来的方法，以及为什么是这样——大部分规则都是踩坑踩出来的。脚本都在 `scripts/comfy/`，用法见 README 的“素材生成（ComfyUI）”一节；这里讲原理。

> 环境：Windows 11，RTX 5080 16 GB，内存 32 GB；ComfyUI 0.38；MiniMax H3 图生视频（首尾帧版 `fl2va`，int8），文本编码器 NVFP4；关键帧编辑用 Qwen Image 2.1。生成 768×1344、24 fps、20 步，一段 124 帧约 10 分钟。

---

## 1. 要解决的问题

桌宠和一般的视频不一样：

1. **要能一直播下去**。她大部分时间停在某个状态（待机、思考、写代码……），一段 loop 要反复播几十分钟。只要能看出“又从头开始了”，就会很出戏。
2. **状态随时切换**。Claude Code 的状态几秒就变一次，任意两个状态之间都要能自然地接上，不能闪、不能跳、不能停顿。
3. **偶尔要有点别的动作**，但不能打断她原本的节奏。
4. **嘴不能像在说话**。视频模型非常喜欢让角色张嘴；桌宠不出声，一张一合就像在默念。
5. **全程本地、无人值守**。几十段素材，要能批量生成、自动检查、失败自动重试。

---

## 2. 整体结构：一张状态图

```
                    ┌── thinking ──┐
                    ├── confirmation
   drowsy ──┐       ├── complete
            ├── 枢纽 A（= idle，坐着，书合上）── waiting（idle + 偶尔看怀表）
   error  ──┘       │
                    │  A ⇄ B 过渡
                    │
                 枢纽 B（书摊开） ── reading
                                  └─ writing
```

- 每个状态有一张**关键帧**（9:16，1026×1824）：她在这个状态下“标准”的样子。
- 状态挂在两个**枢纽**上。枢纽 A 就是 idle；枢纽 B（书摊开）只是一个中转姿势。
- 片段分几类：
  - `loop`：停在某个状态时反复播；
  - `intro` / `outro`：从枢纽进入状态、从状态回到枢纽；
  - `transition`：枢纽之间（A→B、B→A）；
  - `event`：随机小动作，首尾和 loop 一样，中间做点别的。
- 切换状态时，播放器在这张图上找最短路径，按顺序播沿途的片段。例如 thinking → writing：thinking 退出 → A→B → writing 进入 → writing 循环。

**所有衔接都落在关键帧上**：intro 的末帧 = loop 的首帧 = loop 的末帧 = outro 的首帧 = 该状态的关键帧。只要每段片段都“从关键帧出发、回到关键帧”，任意组合都能接上——这是最早的设计，也是后来一切问题的来源（见第 4 节）。

---

## 3. 关键帧

### 3.1 编辑出各个状态

从一张定稿的 idle 立绘出发，用 **Qwen Image 2.1** 编辑出其余状态（`qwen_edit.mjs`，官方模板参数：25 步、CFG 1、euler / simple）。

- 参考图只给一张 idle 当 `<image1>`（画布大小跟随它），**姿势用文字写清楚**。同时再给一张“姿势参考图”时，模型反而不照搬姿势，还会改人物大小。
- 背景用纯青色 `#00B8D4`：后面所有视频都在青色背景上生成，最后按这个颜色抠图。青色和角色的橙发、白裙、棕色书都离得远。
- 坐姿比站姿好：她坐在一叠书上，摇晃时下半身天然稳定，书堆也成了后面对齐用的“锚”。

### 3.2 对齐（非常重要）

编辑模型偶尔会把人物整体挪动或缩放几个百分点。关键帧之间对不齐的话，过渡片段中途整个画面会突然平移一下——我们的第一版 error 关键帧就是这样。

`place_keyframe.py` 以**画面下部的书堆**（静止的道具）为模板，在 ±3% 的缩放、若干像素的平移范围里搜索，把候选图对齐到 idle 关键帧，然后分别存一份青色版（给视频模型）和透明版（给桌宠的占位图和点击区域）。最早试过按人物轮廓对齐，轮廓本身随姿势变化，对不准。

## 4. loop：为什么“首尾同一帧”不行

### 4.1 第一版：K0 → K0

最直接的做法：首帧和末帧都给同一张关键帧 K0，让模型生成中间的“轻轻晃动”。首尾相同，自然就能循环。

结果循环感非常强。原因不在于节奏固定，而在于**模型在首尾帧约束附近会明显减速**：开头慢慢离开关键帧，结尾慢慢回到关键帧，两端速度都趋近于零。每一圈都是“低头……抬头……停住”，再从头来一遍。

试过的补救都不够：

- 提示词写“持续不断、没有停顿”：没用，约束是硬的。
- 导出时把首尾慢的部分加速（`export_frames.py --retime`）：均匀提速会冲到关键帧再折返，反而更像停顿；保留缓入缓出只缩短，能减轻一些，但根上还是“离开—回来”。
- 换成更安静、幅度更小的动作：循环感弱一点，但也几乎看不出在动了。

### 4.2 最终做法：关键帧放在中间

思路反过来：**不让关键帧当端点，而让它出现在一段连续动作的中间**。模型经过它的时候不会减速，因为前后都还有动作。

**第一步，`<状态>-M`（124 帧）**：不给首帧和尾帧，只用 `MiniMaxH3AddGuide` 把关键帧锚在第 61 帧。提示词写一个“没有起止”的持续动作（“像被微风吹着一样，持续、缓慢、平稳地左右轻轻摇晃，一直在动、没有停顿”）。得到一段“晃着过来、经过关键帧、晃着过去”的视频。

**第二步，`<状态>-MB`（90 帧）**：从 M 里取关键帧前后各 45 帧这一段（第 16–106 帧）当作一圈的主体。它的尾巴（第 85–106 帧）和开头（第 16–37 帧）是两段不同的动作，需要一段“接缝”把尾巴接回开头。于是生成 MB：

```
M:   16 ─────────────── 61（关键帧）─────────────── 106
       └ 开头 22 帧 ┐                     ┌ 尾巴 22 帧 ┘
                    │                     │
MB:                 │   [0 … 21] 锚住 M[85…106]
                    │   [22 … 67] 模型自由生成的衔接
                    └── [68 … 89] 锚住 M[16…37]
```

给模型的不是一张图，而是**两端各 22 帧的真实动作**。模型看得到动作的方向和速度，生成的接缝两边速度能接上，不会停。

**第三步，拼接（`assemble_loop.py`）**：在两处引导重叠的范围里各找一个跳变最小的接缝点：M 走到某一帧切进 MB，MB 走到某一帧切回 M。最后把这一圈转到从关键帧（M 的第 61 帧）开始、回到关键帧结束，得到 `<状态>-ML`（约 138 帧，5.75 秒）。

这样一圈的首尾仍然是关键帧，和过渡、事件照常衔接；但在任何位置都没有“停下来”的地方。用户的评价是“完美”，之后所有 loop 都改成了这种做法。

### 4.3 每轮的小变化

- 每个状态做两段 loop（原版 + 眨眼变体，见第 7 节），每轮随机挑一段。
- 每一轮的播放速度在 1 ± 6% 之间随机（`animation.loopRateJitter`），呼吸节奏不会一成不变。
- 试过在播放端整体左右旋转（两条周期不成整数比的正弦叠加），最后关掉了：视频本身已经在晃。

## 5. 过渡：两端也带着动作

第一版过渡是“关键帧 A → 关键帧 B”的首尾帧生成。问题和 loop 一样：两端减速。loop 一直在晃，进入过渡时却像先停住再起身，到达时又停住再开始晃。

**第二版**（`T-<文件名>`，124 帧）：两端不再锚单张关键帧，而是**锚相邻 loop 的帧**：

- 开头 22 帧 = 出发状态 loop 的**开头** 22 帧；
- 结尾 22 帧 = 到达状态 loop 的**结尾** 22 帧。

播放时，出发状态的 loop 播完一圈回到关键帧，接上过渡——过渡的开头正好是“loop 又从头开始了”的样子，然后才慢慢转向新的动作；到达时也是“像 loop 结尾那样”回到关键帧，再接上新状态的 loop。经过同一张关键帧的片段都是“像 loop 结尾那样到达、像 loop 开头那样离开”，怎么组合都带着动作接上。

细节：

- 中间真正的过渡动作约 3.3 秒。动作大的（complete 把书抱到胸前）加长到 158 帧，提示词加“整个动作放慢”，否则中间那一下太急。
- 枢纽 B 上没有状态，也就没有 loop。为了让经过 B 的过渡也能两端带动作，另做了一段**不播放的参考 loop**（`hubB-ML`），只给过渡当锚。
- **error 是一次性状态**（停在关键帧上，不循环），那一端仍然锚关键帧，但锚的是 **5 帧相同的关键帧**（`RepeatImageBatch`）。只锚一张的话，末帧会跳一下，起步也太猛；5 帧相当于告诉模型“这里要定格”。

## 6. 随机小动作：插进 loop，而不是单独一段

### 6.1 第一版：从关键帧出发、回到关键帧

随机事件（打哈欠、张望、敲下巴……）最早也是 K0 → K0：从关键帧出发，做个动作，回到关键帧。问题还是那个：开头和结尾都静止。loop 一直在晃，事件一开始她就僵住了。

### 6.2 插入式

改成**插在 loop 的某一帧后面**（`E-<事件>`，158 帧）：

- 开头 22 帧锚住 loop 第 at-21 到 at 帧；
- 结尾 22 帧锚住 loop 第 at+1 到 at+22 帧；
- 中间约 4.75 秒按剧本做动作。

`assemble_loop.py --insert` 在两端引导范围里找最小跳变的接缝，把它插回 loop：前面是原 loop 的一段，然后是动作，再接回原 loop 剩下的部分。得到“摇一会儿 → 做动作 → 接着摇”的 10.5 秒一段（252 帧），首尾仍是关键帧，登记为 event。播放端每播完一轮 loop，以一定概率改播一段事件，各事件有自己的概率、冷却和分组。

### 6.3 写剧本

- **按秒写**：“0 到 1 秒她安静地坐着；1 到 2.5 秒……；4 到 5 秒回到最初的坐姿”。不写时间，模型会把动作拖满全程或者做两遍。
- **道具从无到有再到无**（借鉴 dsh-pet）：茶杯、墨水瓶这类道具用光点凝聚出来、用完再化成光点散掉。首尾帧一定没有道具，接回 loop 时画面干净；如果写“从腰间拿出来”，模型不知道东西从哪来、放到哪去。
  - 但光点要写“很弱、只在道具周围，不照亮身体，背景颜色不变”，否则会把整个画面照亮，抠图时背景就不是纯青色了。
- **闭眼状态要写瞳色**：drowsy 的 loop 一直闭着眼，锚住的帧里看不到眼睛。惊醒时模型会随便睁出蓝眼睛。提示词写明“琥珀色（橙金色）”，再加一张 idle 关键帧当参考图（`refs`，切到 `MiniMaxH3ReferenceToVideo`）。
- **稳重的性格**：Claude-Chan 的动作都写“从容、不急不慢”。做得快一点会更“有精神”，但不符合角色。

## 7. 眨眼：在 loop 里重新生成一小段

眨眼不能做成单独的随机事件：事件从静止的关键帧开始，眨眼那一下摇晃就停了，非常明显。

做法（`blink.mjs`）：在拼好的 loop 里挑一段（从第 10 帧或第 60 帧开始的 73 帧），两端各 22 帧用原 loop 的帧锚住，只重新生成中间约 1.2 秒，提示词把“眼睛一直睁着、不眨眼”换成“中途自然地眨一次眼”。`assemble_loop.py <状态> --blink <n>` 把它拼回去，得到和原 loop 首尾完全相同、只多一次眨眼的变体（`<状态>-loop-2`），引擎每轮随机挑一段。

## 8. 后处理：让所有衔接逐像素一致

`finish.py` 把生成的帧变成可用的片段：

1. **剪掉首尾多余的静止帧**（持续动作的片段不剪）。
2. **标准帧对齐**：每张关键帧只选一个视频里的“标准帧”（第一次用到它的片段的端点），之后所有片段的端点都在 8 帧内按余弦权重平滑对齐到它。这样任意两段在衔接处像素完全一致。
   不直接用关键帧原图当端点，因为生成画面比原图略软，直接替换会在衔接时“闪一下变清晰”。
3. **抠图**：按青色键色算 alpha（相似度 0.25、过渡 0.04，和 ffmpeg 的 colorkey 一样），再去掉边缘的青色溢色，输出 774×1376 的 VP9 + Alpha。
4. **自动检查，不合格就重来**：
   - **切镜头**：相邻帧差超过中位数 12 倍，模型偶尔会切到脸部特写；
   - **背景漂移**：画面边缘偏离键色超过阈值，长片段背景会慢慢变灰或加暗角。

   这两种都返回退出码 3，批量脚本自动换随机种子重新生成，最多 3 次。

## 9. 导出与播放

- **AVIF**（`export_frames.py`）：宽 540、画质 50，24 fps。同一段过渡 AVIF 约 1.3 MB（WebM 1.7 MB，WebP 6–9 MB），每帧解码约 6 ms。画质 50 的体积约为 70 的一半，桌宠尺寸下看不出区别。
- **点击区域**：所有片段所有帧的不透明区域取并集，缩成 64×114 的粗网格，向外扩一格，作为窗口形状。透明的地方鼠标直接点穿到下面的窗口，没有逐帧开销。
- **播放器**：逐帧解码画到窗口上。下一段在当前段播完前就准备好；因为每段末帧等于下一段首帧，下一段从第 2 帧开始播，避免同一画面停两帧。
- **打断**：intro、outro、过渡一旦开始必须播完；loop 播完这一轮再离开。目标是 confirmation、error 这种急事，或者当前在 idle / drowsy / 事件里，才用约 150 ms 的交叉淡化立即离开。

## 10. 提示词的几条铁律

所有片段都带这两段约束（`jobs.mjs`）：

- **镜头**：“单一连续镜头，固定机位，角色全身始终完整地在画面中，画面不切换、不推近、不出现任何特写，纯青色背景全程不变。”
- **表情和嘴**：“面部表情保持和第一帧一致，嘴唇始终闭合，不张嘴、不说话、不笑出声；无多余手指、无闪烁、无突然跳变、无道具消失。”

另外：

- 持续动作用“一直在进行、没有起止”的动词（摇晃、书写、视线游移），**不要写“先……再回到……”**，否则模型会做成一个来回。
- “望向观众”“询问”“哼歌”会让模型以为在说话。只描述姿势和头部动作，写“嘴唇紧紧抿着”。即便这样，Q 版“哼歌”的嘴还是一张一合，最后放弃了这个动作。
- 道具写清楚大小（“只有她手掌那么大，比她的脸小得多”），否则茶杯会比脸还大。
- 书的动作写“书一直摊开不动，绝对不要翻页”，否则阅读时她会不停地翻。

## 11. 检查

- `scripts/analyze_loop.py`：倒放（回文）、静止帧、首尾是否对齐、和相邻片段的衔接、速度突变。
- `scripts/check_joins.py`：所有**可能连续播放**的片段对（loop→intro、outro→过渡、事件→loop……）逐对检查接缝差异。
- 脸部抽帧图（`contact.py`）：每段抽几帧放大看脸和手——嘴有没有动、手有没有变多、眼睛颜色对不对。自动指标看不出“三只手”这种问题，必须人眼看。
- 速度曲线：最快的半秒不超过平时的约 2.5 倍，否则会显得突然。

## 12. 踩过的坑

| 现象 | 原因 | 解决 |
|---|---|---|
| loop 每圈“低头—抬头—停住” | 首尾帧约束附近模型减速 | 关键帧锚在中间 + 用真实动作锚住的接缝（第 4 节） |
| 状态切换时先僵住再动 | 过渡两端锚单张关键帧 | 两端锚相邻 loop 的 22 帧（第 5 节） |
| 随机动作一开始就停住 | 事件从静止关键帧出发 | 插入式，两端锚 loop 的帧（第 6 节） |
| 眨眼时摇晃停了 | 眨眼做成了单独事件 | 只在 loop 里重新生成 1.2 秒（第 7 节） |
| 10 秒的片段背景变灰、褪色 | 长片段漂移 | 单次生成不超过约 7 秒；检测到漂移自动重试 |
| 片段中途切到脸部特写 | 模型自作主张换镜头 | 提示词写死单一镜头；检测到切镜头自动重试 |
| 过渡中途整个画面挪一下 | 关键帧之间没对齐 | 以书堆为模板对齐所有关键帧 |
| 衔接时“闪一下变清晰” | 端点直接换成了关键帧原图 | 用视频里的标准帧对齐，不用原图 |
| 惊醒时睁出蓝眼睛 | 锚住的帧都闭着眼 | 提示词写瞳色 + 参考图 |
| 变出茶杯时整个人被照亮 | 光效太强 | 写明光点很弱、不照亮身体 |
| Q 版抱头蹲防像有三只手 | 关键帧里双臂交叉挡脸，耳边又有一只手，视频照着画 | 关键帧改成双手一左一右按在头顶、手臂不交叉 |
| 加速后反而有停顿感 | 匀速冲到关键帧再折返 | 不再事后提速，从生成上解决 |
| K0→K1→K0 两段拼一圈 | 两段动作幅度对不上 | 放弃，改用第 4 节的做法 |

## 13. 一套素材的工作量

以原版为例：9 张关键帧；8 个状态的 loop 各 2 段（M + MB 生成两段、拼一段，再生成一段眨眼）；7 个状态的进出场 + 2 段枢纽过渡；二十多段插入式随机动作。算上 M、MB 这些中间片段和失败重试，一套要生成七十段左右，每段约 10 分钟（换成 NVFP4 文本编码器之前约 17 分钟），合计十几个小时，基本都在夜里无人值守跑完；人要做的是挑关键帧、写剧本，以及最后逐段看一遍。
